# Remote Gallery Security Policy (Phase 1)

Security is paramount in the Remote Gallery system. This document outlines the security boundaries, authorization checks, RLS policies, rate limiting, and cryptographic controls implemented in Phase 1.

---

## 1. Explicit Consent & Authorization Boundary

The Remote Gallery system is strictly for explicitly authorized personal devices:
* **No Silent Authorization**: Simply logging into an account on a device does not authorize it for the dashboard.
* **No Bypassing RLS**: The mobile app interacts with the database using its authenticated JWT, preventing unauthorized modifications.
* **No Service Role Keys on Client**: Service role credentials are never shipped to the Android client. Database changes bypass RLS only through secure, server-side API routes.

---

## 2. Multi-Layer Authorization Checks

Verification is implemented at multiple layers to prevent privilege escalation:

```
[ Client UI (React Router) ] ──> Checks profile.is_admin. Redirects non-admins.
             │
             ▼
[ Database (RLS Policies)  ] ──> is_admin() helper enforces profile table constraints.
             │
             ▼
[ Server-Side API Routes   ] ──> Re-verifies access token, checks database `is_admin` flag.
```

### A. API Protection
All administrative routes `/api/admin/*` perform server-side checks:
```typescript
const supabase = await createClient()
const isAdmin = await isAdminServer(supabase)
if (!isAdmin) {
  return NextResponse.json({ error: 'Forbidden' }, { status: 403 })
}
```
Any client attempting to bypass UI guards will receive a `403 Forbidden` response.

---

## 3. Cryptographic Pairing Verification

* **SHA-256 Code Hashing**: The raw pairing codes (e.g. `A7K9-29MX`) generated by administrators are never stored in the database. Instead, the server stores a SHA-256 hash of the code. This prevents database compromises from leaking pending codes.
* **No Logging**: Raw pairing codes are never printed to console logs or stored in audit tables.
* **Single-Use Enforcements**: Once a pairing session is redeemed, `used_at` is updated. Any subsequent verification attempt on that code is rejected.

---

## 4. Rate Limiting

To prevent brute-forcing of the 8-character pairing codes, the `/api/device/pair` route implements an in-memory sliding window rate limiter:
* **User-Level Restrictions**: Keyed by the authenticated user's ID (`user.id`) rather than IP, preventing brute-forcing even if requests are distributed across multiple network interfaces.
* **Lockout Period**: If a user submits more than 5 incorrect pairing attempts, their account is locked out from pairing for 15 minutes.

---

## 5. Audit Logging

Every sensitive operation creates a detailed audit entry:
* **Logs Generated**:
  * `DEVICE_PAIR_GENERATE`: Generated when an admin creates a new pairing code.
  * `DEVICE_PAIR`: Generated when a device successfully redeems a code and pairs.
  * `DEVICE_UNPAIR`: Generated when an admin revokes authorization.
* **Sensitive Data Redaction**: Passwords, tokens, pairing secrets, and image data are strictly banned from inclusion in the audit logs.
